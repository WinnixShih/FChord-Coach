討論 A MediaPipe 跑在哪裡？（最重要） 需雙方決定

這個決策決定你的 FastAPI 要接收什麼資料，也決定整個系統的延遲表現。 MediaPipe 是負責「看到手、給出 21 個關節座標」的工具，它可以跑在手機上或是你的 server 上，兩者有明顯差異。

方案 X — Server 上跑 MediaPipe
手機傳圖片給後端
每幀把相機截圖壓縮後傳給 FastAPI，Server 跑 MediaPipe 取得座標，再跑 GNN 分類，回傳 JSON。

問題：圖片資料量大，網路延遲難以達到 30ms 目標。優點：你朋友直接在 server 管所有 AI 邏輯。
方案 Y — 手機上跑 MediaPipe（建議）
手機傳座標給後端
手機端跑 MediaPipe 取得座標（21 個小數字），把這些座標傳給 FastAPI，Server 只需跑 GNN 分類，回傳 JSON。

問題：Flutter 的 MediaPipe 套件目前不成熟。優點：延遲低，後端邏輯簡單很多。
你的問題 「Flutter 有沒有辦法跑 MediaPipe？我查到官方套件還沒正式釋出，第三方套件也不穩定。如果手機端跑不了，我們 Server 接圖片的話延遲會有多嚴重？有沒有辦法用降幀或壓縮解決？」
討論 B D-04：座標換算確認由你負責 前端負責

你朋友的 AI 輸出的骨架座標是 0 到 1 之間的比例值（normalized），例如 x: 0.35, y: 0.62。 但 Flutter 的 CustomPainter 需要實際像素座標才能在螢幕上畫圖。換算邏輯由你在 Flutter 端處理，不需要朋友介入。

換算公式
很簡單，一行搞定
實際 x 像素 = normalized_x × 螢幕寬度
實際 y 像素 = normalized_y × 螢幕高度

由你在 Flutter 的 CustomPainter 裡處理，你朋友只需要確保輸出的座標都在 0–1 之間。
你的問題 「nodes 和 ghost_nodes 的座標你確認都是 normalized 0–1 嗎？有沒有可能超出這個範圍（例如手離開鏡頭邊緣時）？我這邊需要做邊界保護。」
討論 C JSON Schema 逐欄位確認 需雙方對齊

你們的整合靠這份 JSON 契約，現在先對齊草稿，之後才能各自平行開發。每個欄位你都要清楚它的用途，因為你要在 Flutter 裡接收並渲染。

草稿 Schema（每幀回傳一次）
nodes: float[21][3] — 21 個關節 [x, y, z]，normalized 0–1
node_status: int[21] — 每節點狀態：0=正常, 1=警告, 2=錯誤
label: string — GNN 分類結果，如 "err_index_low"
confidence: float — 分類信心度 0–1
ghost_nodes: float[21][2] — 目標 F chord 骨架（靜態）
error_duration_ms: int — 連續錯誤持續時間（ms）
suggestion: string | null — VLM 建議文字（非同步）
frame_ms: int — 本幀推理耗時（ms）
你的問題 「ghost_nodes 是每幀都傳還是只傳一次就快取？suggestion 是在同一個 response 裡回傳還是另一個獨立的 API call？label 目前有哪幾個值，我需要知道完整清單才能在 UI 上對應顯示文字。」

會議後你的建議開發順序
01
裝好 Flutter 環境，跑出相機畫面
Flutter SDK + Android Studio + VS Code。能看到相機畫面就算第一個里程碑，後面都是往上疊。
02
架起 FastAPI，開 /infer endpoint 回傳假 JSON
你有 C# ASP.NET 和 Express 背景，FastAPI 半天上手。先回傳假資料，不等朋友的 model。
03
Flutter 串 API，用假 JSON 把 overlay 跑通
CustomPainter 接收假的 nodes 和 node_status，畫出骨架和顏色。UI 邏輯驗證完畢後，換成真實 API 只需改 URL。
04
朋友交付 ONNX 後，替換假資料為真實 model
FastAPI 載入 ONNX，接收座標跑真實推理。端對端測試 frame rate 是否達標。
05
加入 VLM 串接、限流、Progress screen
錯誤超過 3 秒觸發 VLM API，加上 rate limiter（max 2 calls/min），$50 預算監控。Progress screen 串 SQLite。
